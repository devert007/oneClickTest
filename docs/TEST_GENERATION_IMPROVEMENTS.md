## 2. Архитектуры генерации

### A. Текущая: single-shot RAG

```
Документ (полный) → Один промпт → LLM → JSON
```

**Проблемы:**
- Длинный документ → обрезается или уходит за context
- RAG добавляет релевантные чанки, но промпт уже содержит весь документ — дублирование
- Один сбой — весь тест невалиден

### B. Multi-step: генерация по чанкам

```
Документ → Разбить на чанки → Для каждого чанка: промпт → LLM → JSON
→ Объединить вопросы → Дедупликация → Случайная выборка N вопросов
```

**Плюсы:**
- Каждый чанк в пределах context
- Меньше «забывания» длинного текста
- Можно параллелить (если есть несколько инстансов LLM)

**Минусы:**
- Больше вызовов LLM
- Нужна логика объединения и дедупликации

### C. Two-stage: экстракция + генерация

```
Этап 1: извлечь ключевые факты из документа (JSON)
Этап 2: по списку фактов сгенерировать вопросы
```

**Плюсы:**
- Чёткое разделение: факты → вопросы
- Легче контролировать качество
- Можно кэшировать факты для одного документа

**Минусы:**
- Два вызова LLM
- Сложнее реализация

### D. Agentic: агент с инструментами

```
Агент: читает документ по частям → выбирает стратегию → генерирует вопросы
→ проверяет себя (есть ли ответ в тексте?) → исправляет при ошибках
```

**Плюсы:**
- Максимально гибко
- Самоисправление

**Минусы:**
- Сложно, много вызовов
- Подходит для больших моделей (7B+)

## 3. Prompt Engineering

### 3.1. Базовые принципы

1. **Структура:** задача → контекст → формат → ограничения.
2. **Few-shot:** 1–2 примера для малых моделей сильно улучшают результат.
3. **JSON:** явно требовать «только JSON, без markdown».
4. **Chain-of-Thought:** для 7B+ моделей — «сначала план, потом ответ».

### 3.2. Готовые варианты промптов

В `api/test_generation_prompts.py` добавлены:

- `build_basic_prompt` — укороченный, понятный
- `build_few_shot_prompt` — с примерами
- `build_cot_prompt` — с пошаговым рассуждением
- `build_chunked_instruction` — для multi-step по чанкам

### 3.3. Ограничение длины документа

- Для 1B: `document_text[:8000]` — ~2K токенов
- Для 8B: `document_text[:16000]` — ~4K токенов
- Для 32K context: можно до ~30K символов

## 4. Structured Output / JSON Mode

### Ollama

- Нет нативного JSON mode.  
- Решение: жёсткий промпт + `format` в API (если поддерживается).

### vLLM / OpenAI-совместимые

- `response_format: { "type": "json_object" }` — снижает вероятность невалидного JSON.

### Fallback: retry + repair

```python
for attempt in range(3):
    try:
        data = parse_and_validate_test_json(response, ...)
        return data
    except ValueError:
        # Отправить в LLM: "Исправь JSON: {broken_json}, ошибка: {e}"
        response = repair_json_llm(response, error)
```
